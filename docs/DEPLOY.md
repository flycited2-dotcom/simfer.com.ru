## Сборка

Node.js используется только на компьютере разработчика. На веб-хостинге он не нужен.

```sh
npm ci
npm run build
php tools/update-sitemap.php
npm run check
npm test
npm run release
```

Для `npm test` нужен PHP 8.1+ в PATH или переменная `PHP_BIN` с путём к исполняемому файлу PHP. Тестовые серверы слушают только loopback, реальная почта в них отключена; положительный сценарий использует изолированный fake-mail. Тесты работают с временными каталогами, не с опубликованными статьями.

Реквизиты редактируются в `content/site.json`. После добавления ОГРН/адреса повторить сборку: они попадут в видимый блок главной и JSON-LD всех шести страниц. Тексты направлений — `content/directions.json`; HTML направлений генерируется из него.

`npm run release` создаёт новую соседнюю папку `simfer-seo-release-*` с публичными файлами и выводит её путь. Архив исходных версий, `.git`, `content`, `docs`, `scripts`, зависимости и статьи в неё не включаются. `tools/update-sitemap.php` входит в релиз и защищён от HTTP-запуска.

## Порядок загрузки на Sprinthost

1. Узнать реальный document root домена в панели. До изменений скачать резервную копию текущих файлов и `.htaccess` за пределы публичной папки.
2. Сравнить существующий `.htaccess` с подготовленными правилами. Сохранить действующие настройки хостинга, объединив правила канонизации. Не затирать неизвестный конфиг вслепую.
3. Загрузить содержимое релиза в корень сайта с заменой одноимённых файлов. Не синхронизировать с удалением. Не удалять и не заменять `articles/`.
4. Проверить PHP 8.1+, работу сессий и право записи в document root для обновления sitemap. Файлы должны быть доступны для чтения веб-сервером; не устанавливать права 777.
5. Запустить генератор sitemap на живом document root, чтобы он учёл **реальные опубликованные статьи**, которых нет в локальном релизе.
6. Настроить периодическую задачу и проверить реальную форму с владельцем почтового ящика. Переданный серверу запрос ещё не подтверждает доставку письма.

## Обновление sitemap после автовыкладки

Робот Claude владеет папкой `articles/`: эти правки её не создают и не изменяют. Ссылка «Статьи» ведёт на `/articles/`; индекс раздела должен публиковать робот. До его публикации адрес может возвращать 404.

После добавления/удаления статьи запускать на хостинге:

```sh
php /ABSOLUTE/DOCUMENT_ROOT/tools/update-sitemap.php
```

В качестве страховки добавить тот же запуск в планировщик Sprinthost каждые 5 минут. Путь PHP и document root берутся из аккаунта, пример с заменяемыми значениями:

```cron
*/5 * * * * /PATH/TO/php /ABSOLUTE/DOCUMENT_ROOT/tools/update-sitemap.php
```

Это инструкция настройки, не уже установленный cron. Генератор сканирует HTML, включая `articles/`, пропускает служебные папки, симлинки и `noindex`. Canonical должен совпадать с реальным HTTPS URL: `index.html` представляет каталог со слешем, остальные `.html` остаются именованными файлами. Несовпадающий canonical пропускается с предупреждением. Обновление XML атомарное, параллельные запуски сериализованы. Статьи только читаются.

Робот должен добавлять своим страницам собственные title/description/H1, canonical, OG и JSON-LD; генератор sitemap не изменяет HTML статей.

## WWW и HTTPS

`.htaccess` учитывает `HTTPS` и `X-Forwarded-Proto` для обратного прокси Sprinthost. Домен назначения фиксирован; исходные путь и query string сохраняются. Прямые `index.html` приводятся к URL каталога.

Openresty/nginx может отдавать статику до Apache. После загрузки отдельно проверить главную, именованную HTML-статью, CSS, картинки, robots и sitemap на www. Если они обходят `.htaccess`, необходимо включить каноническое перенаправление на фронтенде/в панели Sprinthost; один HTML-файл это не исправит.

Основания: [HTTPS и .htaccess](https://help.sprinthost.ru/howto/htaccess), [веб-серверы Sprinthost](https://help.sprinthost.ru/how-hosting-work/webservers).

## Форма

`request.php` принимает компанию (необязательно), email и текст/ссылку. Загрузка вложений на сервер не реализована: для файла указан email компании. CSRF и лимиты работают через сессию; без JavaScript доступна отдельная серверная форма. При ошибке текст сохраняется. Серверный получатель — `info@simfer.com.ru`, отправитель — `no-reply@simfer.com.ru`, адрес посетителя используется только в проверенном Reply-To.

Проверить существование/допустимость отправителя, sendmail и SPF/DKIM/DMARC аккаунта. Без этих проверок нельзя утверждать, что почта доставляется. При недоступной отправке возвращается 503, при слишком частых отправках 429. Ограничение действует в пределах сессии; защита хостинга от массового спама настраивается отдельно.

Проверка на Sprinthost: заполнить одну согласованную тестовую заявку, убедиться в её получении в нужном ящике и папке «Спам», проверить Reply-To. При ответе 200 текст сообщает лишь о принятии почтовым сервером.

## Live-проверки

```sh
curl -sI https://simfer.com.ru/robots.txt
curl -sI https://simfer.com.ru/sitemap.xml
curl -sI 'https://www.simfer.com.ru/klimaticheskoe-oborudovanie/?utm_source=test'
curl -sI 'https://www.simfer.com.ru/index.html?utm_source=test'
curl -s https://simfer.com.ru/ | grep -c -E 'rel="canonical"|og:title|application/ld\+json'
```

Ожидаются 200 для SEO-файлов; 301 и Location на HTTPS без www с сохранёнными путём/параметрами; минимум 3 совпадения metadata на главной. Дополнительно открыть 5 направлений, форму без JS и проверить отсутствие потерь опубликованных статей.
